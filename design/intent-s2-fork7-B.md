# FORK-7 — must every variable have a name? (designer B)

## For Ev

**Recommendation (likely): no name is required, but no variable may be unspeakable. A variable is spoken one of three ways: by its name; by its one reader, when it has no name; or by the operation and port that define it, when it is an output. So: a variable without a name has exactly one reader (a slot or a definition) and belongs to it; the moment a second reader wants it, the person names it.** The kernel still mints no name and the GUI proposes none (your choice-7 ruling stands and this needs it). Every surface keeps its one-step spelling for a lone number; only *sharing* costs a name, and sharing is where a name earns its keep.

**Premise check.** "Anonymous" does two jobs today, and that is the flaw the question points at. (1) *A literal with an identity*: `12 mm` typed in a depth slot, `5 mm` inside `w + 5 mm`, a `3` in a count slot. The slot or the definition is its whole description, and VR2 already speaks it that way ("5 mm, the depth of Extrude"). (2) *A shared thing with no handle*: the same unnamed variable read by two slots, reached through the offer in #4247, through a Python `VarId` passed twice, or through an edit's fresh table. Job (2) is what forces everything you flinched at: the reader-label on the offer's buttons (which reader, when there are two?), the `#hex` tag in diagnostics, choice 9's "nothing shows that two slots share" (a drag then moves an invisible twin), VR7's reader *counting* with cascade rounds, and a lossy text door: `Doc::unparse` writes an unnamed variable as its value (`5 mm`), so re-parsing the formula mints a new one and a share through it breaks silently (likely; from the doc comment on `Doc::unparse`, not traced through the GUI's text commit). The corpus already lives under the narrower rule: 225 free variables, 3 named, none unnamed with two readers (likely; a textual reader count over the files). Outputs (not yet built on main; `VarDef` is still `Free | Defined`) are a third case: their operation speaks them, so a name on one would say the same thing twice.

**The rule as a final state ("owned or named").**
- A variable has a name, or exactly one reader, or is an output. The reader may be a slot or a definition, and an unnamed definition in a slot may own unnamed quantities of its own: a tree hanging off one slot, with no identity anyone else holds.
- *Who names*: the person (GUI), or the caller (`declare_var(name, …)`, which already requires one). Never an operation, never the kernel.
- *Doors*. Typing or writing a lone quantity mints an owned variable, as today. Making a second slot or definition read an unnamed variable refuses `SharedVarNeedsName`; the GUI's accept-offer and Python's share-by-id supply the name in the same edit. Clearing the name of a variable with two readers refuses. `DeclareVar` keeps requiring a name, so no unnamed variable is ever declared, only written in place. A fresh-table entry (the variables one edit mints for its own formulas) is a declaration and carries a name; a quantity read once is written inline instead, so `Fresh` stops being an anonymity door.
- *Lifecycle (VR7, simpler)*: an unnamed variable goes with its reader, when the reader is deleted or rewritten; no liveness count, no rounds. The load walk checks "unnamed ⇒ one reader" where it checks "unnamed ⇒ read" today.
- *Outputs*: spoken as "the body of Extrude "plate"", a name optional and never required; many readers allowed, because the operation is their handle.
- *Formulas* (VR6): `w + 5 mm` stays writable; the `5 mm` belongs to the definition. Unparse writes it back as `5 mm` and the round trip is now exact in meaning, because nothing else held that identity. Constants (`turn/4`, `2`) unchanged.
- *Python / Rust*: `extrude(depth=12 * mm)` unchanged. Sharing is `declare_var("depth", 12 * mm)` then the name or id in each slot; passing an unnamed id twice refuses with the name it needs.
- *Split and inline*: an owned variable moves or carries with its reader and can never collide, so FORK-6's `VarNameConflict` is confined to the variables the person deliberately shared, which the refusal can list. Inlining a second copy of a part collides on exactly those.
- *The GUI (#4247)*: choice 3 stands (named and unnamed equal values are both offered); accepting an unnamed one opens the empty name field, and Enter commits name and read as one step. Choice 8's `name…` button stays as the promote door. Choice 9 is answered for free: a shared slot reads a named variable, and shows the name.
- *Migration*: none. No corpus file holds a shared unnamed variable; the stricter load walk refuses one typed, with the regenerate recourse, as VR9 says.
- *Reversible*: yes. Tightening later to "every free variable is named" is one more refusal at the slot doors; loosening back is removing one.

**The alternative you asked about: every free variable is named** (outputs and in-slot definitions exempt, since their definition speaks them). It is defensible, and it makes one thing true the recommendation does not: every number in the model appears in the variables list under a word the person chose. Where it bites, sure:
- *Gestures*. A drawn profile segment, a datum, an extrude inserted by a tool: every slot they create needs a name before the node can exist, or the node sits unresolved until named, or the tool invents a name (VR2 forbids it, and you rejected `distance_1`). In the golden document 53 of 89 free variables are profile-step arguments and 15 are datum offsets; a sketch becomes a naming session.
- *Scripts and tests*. About 700 Rust sites and 100 Python sites write a quantity straight into a slot; each becomes a declaration, and test code acquires a name-minting helper of its own.
- *Formulas*. `w + 5 mm` is unwritable in one step: declare `margin` first.
- *Inline*. Every variable of a part is named, so a second instance of the same part collides on all of them; inline needs a rename map on every call.
- *The panel* lists every dimension of every sketch, and the knobs that matter drown in them.
- Nothing it buys is lost under the recommendation: no variable is unspeakable, no name is invented, and sharing is visible. I would not take it; if you want it anyway, the recommendation is its first half and the second half is one refusal more.

Two other readings, dismissed: naming outputs (says the definition twice; "the body of Extrude "plate"" is already a handle, and names are for formula text); and a GUI-only requirement with the kernel unchanged (a representable state the GUI merely avoids; the invariant belongs at the door and the load walk).
