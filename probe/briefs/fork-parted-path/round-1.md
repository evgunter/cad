# The parted path: round 1

Three designers weighed one statement of the problem independently. Their first reports are beside this file, labelled `A.md`, `B.md`, `C.md` (`git fetch origin boxfinish/briefs`, then `git show FETCH_HEAD:probe/briefs/fork-parted-path/<label>.md`). The message that sent you here says which label is yours. Read the other two in full.

## Where the three stand

All three agree on this much: a `FlipCrossing` names what turned, by type, so an empty one cannot be built; `FlipEvidence::is_empty` and the range search's `FlipUnfounded` go; a parted leaf is never a `FlipCrossing`; and the kernel disagreeing with itself is a question for a test instrument (a zero-width replay at the witness), not a mass of a document.

They differ on what the certificate COMPARES, and so on what two of the three states are:

| | A | B | C |
|---|---|---|---|
| The gate compares | the choices | the build (per node, standing and names) | the whole record, checks included |
| A check with another definite sign, choices equal | the witness's build: certifies | the witness's build: certifies | a turn: refused `FlipCrossing`, named, role carried |
| Check sequences differ, choices equal | certifies | certifies | parted: unsettled, bisect |
| Choices part at a pruning query | bisect | certifies if the build is the same, else `FlipCrossing` naming the first node | unsettled, bisect |
| Choices part elsewhere | a kernel defect: fail loud (bisect until every steering branch is logged or marked) | as above | unsettled, bisect |

## What this round asks of you

1. **What moved you**, if anything, and to where. State your recommendation again as a final state, in a few lines, even if unchanged.
2. **Is your own first argument answered** by either of the others? Say which of their arguments you accept, which you reject, and why. In particular:
   - C does not recommend comparing choices only, because the certificate would then rest on every role stamp being right, and says the side reader's rays are checks whose combined answer steers the build. A and B: is that so, and if it is, what does your gate make of it?
   - A and B say comparing checks with the witness tests the kernel's two lanes against each other, not the document, and that a parity instrument does that better. C: what does the whole-record gate buy that the instrument does not?
   - B gates on the build and names its own unknown: whether a node's standing and name tables state everything "the same build" must mean. A and C: if they do, is B's the right final state? B: if they do not, what is the gate?
   - A calls a parting away from a pruning query a kernel defect; C bisects it; B does not need to classify it. What should a consumer be told, and what does it cost at the floor?
3. **Facts the three contradict each other on.** Check each against the tree (read, or run if it is cheap) and report what you find, with the place:
   - Does any check pass with either definite sign, so that "choices agree, one check has the other sign" can come from geometry? (C: an edge's convexity read at rest. B: `props_verdict_shapes.rs` row 3. A found no call site.)
   - Do the extra candidates a box-scalar pruning query hands on log decisions? (`VerdictVector`'s doc says they "decide nothing about them"; the slid-block passage in `resolve/vdiff.rs` reads otherwise.)
   - Is a lane choice (DESIGN `[verdicts.consumers]`: "picks a form for one certified statement the body has either way") logged as a choice, so that a turned one refuses a leaf whose build is the witness's?
4. **What would have to be measured** before a lane builds your final state, in the order you would want it.
