## The unit
The evaluator reuses a node's result when its content key matches a prior evaluation's: `[determinism]` says equal keys mean equal inputs, so the key is the proof. At the symbolic scalar that is false in two ways, and the next units (a store of node results across a drive's leaves) rest on it being true.

**Build, as ratified:**
1. **The content key at a symbolic scalar hashes the expression as well as the number.** `ContentBits for Sym` feeds the value's bits only, so two inputs with equal numbers and different expressions (two variables that happen to hold `10 ± 0.1`) have one key, and a result built from one would be served for the other with the first one's identities. A symbolic node id is a content hash of its expression (the module docs), so it is the thing to feed; say what feeding it means for a nested scalar (`Sym<Dual<…>>`, `Sym<Interval>`, `Sym<f64>`) and write the one sentence per `ContentBits` impl.
2. **A value with no expression is named by where it was minted, not by a per-replay counter.** `Sym::opaque` takes its name from `OPAQUE_SEQ`, which restarts with each replay: two replays can give one name to two different numbers, and once a value crosses replays `opaque(a) − opaque(b)` under one name is the zero polynomial, a false theorem. The ratified answer names it by the node that minted it and its ordinal there. `geom-core` does not know the evaluator's nodes: find the smallest honest mechanism (a mint scope the evaluator opens per node and the tier reads; what a mint outside any scope is named by; what "ordinal" means when a node's op is retried or a ladder re-runs part of it). Two mints at one (node, ordinal) in two replays may hold different numbers when the node's inputs differ: say why that is sound (the key differs, so the results never meet) or find where it is not.
