## MAJOR

**MAJOR-1 — a canceled run LANDS as the current document's answer, blanking the feature tree and darkening the busy indicator.** `DocSession::land` (session.rs:356) compares generations and nothing else. A run canceled for the CURRENT generation — exactly what the toolbar's Cancel produces (app.rs:287 → `CancelEvaluation` → `eval.cancel()`; the in-flight job's generation IS `self.generation`) — passes that comparison, so its empty prefix replaces the last good `Evaluation`. `EvalDone::completed()` (evalseam.rs:98) is called **only from tests**; nothing in `src/` reads it. Measured e2e: before Cancel `busy=true landed=Some(2)` with three `[ok]` rows; after Cancel + `pump()` `busy=false landed=Some(7)`, every row `[—]` (Unevaluated), `has_faults=false` — the panel says "not building anything, and not waiting for anything". `sync_scene` then rebuilds from the empty evaluation, leaves a `scene: NoProduct(..)` status, and nothing re-submits: the tree stays blank until the next edit. Contradicts evalseam.rs:29–32 ("never mistakes it for a completed one"), falsifies claim 2's `busy()` in meaning if not in letter, and misses GUI-3-SPEC deliverable 3 ("cancel token honored") and its acceptance line ("busy + cancel work"). Row: `a_canceled_run_is_not_mistaken_for_the_current_documents_answer`.

**MAJOR-2 — `ThreadEvaluator` does not coalesce, so the two seam implementations do not agree and the module doc describes the one the application does not run.** evalseam.rs:22–25 says submits COALESCE, "only the newest document is queued … at most one evaluation per completed run rather than a backlog". `InlineEvaluator` holds one `Option<EvalRequest>` and does that; `ThreadEvaluator::submit` (evalseam.rs:290) sends every job into an unbounded `mpsc` and increments `in_flight`, so N submits queue N jobs, run N `evaluate` calls, return N results. The row naming the property — `eval_seam::an_edit_during_an_evaluation_cancels_and_restarts_rather_than_queueing`, asserting "the superseded request produced no second result to discard" — drives `InlineEvaluator` only; the single threaded row submits once and can never see it. The consequence is bounded (superseded jobs are pre-canceled, return instantly, `pump()` drains in one call, the session discards by generation), so this is a falsified claim plus a false module doc rather than behavior a user would name — but claim 2 asserts both halves and both are false for the lane `ViewerApp` constructs (app.rs:174). Row: `both_seam_implementations_coalesce_two_submits_into_one_result`.

## Claims disposition

Save writes the current path only (checked through the FILE, not `path_edits()`); open→save is byte-identical (I assert file bytes, which the shipped rows do not); a replayed history undoes one logged edit at a time to the root, then refuses.
2. **Evaluation seam — FALSIFIED in two places.** Cancel-and-restart, generation staleness (including a future-generation result), the memo living inside the seam (`reused > 0` across an edit the session never memoized), and the token-travels-with-the-job argument all hold.
