# Fork: what a blend does with other features in its band's region

## For Ev

**Recommendation (likely):** adopt Boolean semantics as the blend's *specification* now — a convex blend is `S − R`, a concave one `S ∪ F`, where `R`/`F` is the band's region as `blend/reach.rs` already defines it (a closed set: the material between the band surface and its supports' strips, over the band's full extent, cut off at its end faces). Every case then follows from set algebra, with no per-case rule: a feature wholly inside goes (hole, bar, pin, boss, void, island, and a free solid in `R`); a hole whose mouth the fill covers is sealed (a through-hole turns blind, a blind hole becomes a void); a crossing feature **refuses typed as a coverage frontier, not as a semantic exception**. Build it as today: in-place surgery for everything wholly inside or sealed, plus the op-agnostic lint. Do not build C2 (the blend as a literal Boolean), and sequence C3 (the Boolean's crossing lane called on the band face) *after* the kernel's intersection table serves the band×feature pairs — which is the same moment the "blend first, then drill" reorder starts building for fillets.

**Premise corrections, first.**

1. *"If we take C1 we should not shoot for Boolean semantics" is a false fork.* A semantics is what the result IS; a refusal is what the builder cannot yet produce. The Boolean itself refuses most curved pairs (`geom-brep/README.md` C5: implemented plane×{plane,sphere,cylinder,cone,torus-axis-aligned,NURBS}, sphere×{sphere,cylinder}, declared-equal cylinder×cylinder; "every other pair refuses") and is still a Boolean. Stating the blend's result as `S − R` and refusing where the band would have to be trimmed by a feature is exactly D4's fail-loud discipline, and it fixes the meaning so coverage can grow without re-ruling. C1/C2/C3 are build states of one rule, not three rules. (sure)

2. *The reorder recourse is one line in the API and two edits in the editor — but the body it asks for mostly refuses at the Boolean today.* On main every operand slot is a read re-pointed by `DocEdit::SetParam` with a `SlotValue::Read` (DM6 now reads "no edit infers a re-point", `crates/editor-core/REFERENCES.md`); so `fillet(subtract(body, hole))` → `subtract(fillet(body), hole)` is two `SetParam`s, or one line in Python. The clunkiness Ev asked about is not the edit. It is that `subtract(fillet(body), hole)` has the hole's cylinder crossing the band face: a plane–plane *fillet* band is a cylinder with its axis along the edge, so the pair is skew cylinder×cylinder; a curved-support fillet's band is a torus. Both route to the unimplemented general rung (`geom-brep/src/intersect.rs`, `route`: cylinder×cylinder "unequal, undeclared, or skew routes to the general rung, whose arm has not retired"; cylinder×torus "implemented: false"). Only a *chamfer* (plane strips, plane×cylinder served) drills after. So for a fillet, neither order builds the crossing body today, and the frontier is one SSI frontier seen from two doors. (sure)

3. *Do the fillet's edge selections survive the move upstream?* Names are stable from birth (D5) and are not re-derived from position. An edge the hole did not touch keeps its extrude-minted name and resolves on the pre-hole body: survives (sure). An edge the hole *split* is named `Fragment(...)` composed over the Boolean's output (`names/README.md`, "yields n fragments, `Fragment(Qualifier)` follows the parent-bearing segment"); re-pointing the fillet past the Boolean strands it — reported `Maintenance::Strand` with `Took::Reach` ("re-pointed a read past {node}, which minted the name", `edit.rs`), never refused, and the fillet then refuses at evaluation until a `Rebind` to the whole edge. How often: only when the hole's wall meets the *requested* edge itself, which is a sub-case of crossing; in the wholly-inside and sealed-mouth cases the feature's cycles lie inside a cap or support strip and the chain's edges are untouched, so the names survive. (likely)

**The rule, case by case (final state).** Terms: *band region* = `R` (convex, removed) or `F` (concave, added); *feature* = a connected set of faces the chain does not blend; *mouth* = a cycle on a face bounding the region.

| Case | Result under `S − R` / `S ∪ F` | Build |
|---|---|---|
| Feature wholly inside `R` (through-bore, blind bore, dimple in a strip) | goes with the removed material | through-bore built (steps 1–4, `blend/consume.rs`); blind and support-hosted: new readings, same carve |
| Feature wholly inside `F` (bar, pin, boss) | absorbed by the fill | the bar is step 3's carve with the material side flipped; one-cycle members as above |
| Mouth on a cap or strip, hole outside `F` (**S**) | **sealed**: plug face over the mouth; through→blind (`mfkr`, same shell), blind→void (`mfkrh`, new shell via the sealing door) | new door in `topo::voids` |
| Void wholly inside `R` | removed | shell-removal door beside `insert_void` |
| Island (second solid of the part) wholly inside `F` | absorbed | same door |
| Free solid wholly inside `R` | removed (a subtraction takes everything in its tool; the designers' side rule is dropped) | same door |
| Any feature crossing `∂R`/`∂F` | refuses `FaceClearance`/`RingClearance`, `bounded: false` — a frontier | C3 later, see order |

Why seal rather than refuse (S2 over S1): order carries intent. `fillet(subtract(b,h))` seals the exit; `subtract(fillet(b),h)` keeps it open. Refusing deletes one of two expressible bodies, and the lint supplies the "loud" S1 was reaching for. The convex analogue is already built: a bore's cap ring promoted to a plug face is `consume.rs`'s first step. S2 can be reversed to S1 later by one refusal arm; S1 cannot be reversed without this design again.

Why not C2 (region as a tool body, run the Boolean): the tool is a cusp-edged sliver — wedge 0 along both trimlines — and the Boolean's declared-cusp family is "DEFINED AND UNBUILT" (`topo/src/boolean/rim_wedge.rs`); declared coincident faces must be planar (`BooleanDeclarations` doc), so a ruled band's cylindrical strip cannot even be declared; tangent side-cover reaches only plane×cylinder through a strut (`tangency_certifies_side`, `boolean/mod.rs`); and every band×feature pair beyond plane×cylinder is C5-unimplemented. C2 lands nothing a fillet user can reach and discards the carve that works. (sure on the facts; sure on the rejection)

Why not C3 now: cutting the crossing feature against the band face is the same SSI pair (skew cylinder×cylinder, cylinder×torus) the Boolean lacks. When those arms retire, C3 is "call the Boolean's crossing lane on one face" and the reorder also builds; before that it is a second marcher. Sequence it behind C5's arms. (likely)

**What the user sees.** Wholly inside / sealed / closed shell: builds; the lint reports it. Crossing: refuses, with the sentence conditioned on coverage — for a chamfer, or a feature that would clear the band after reordering: "blend before <feature>"; for a fillet band whose pair is unserved: "no order of these operations builds this body yet: <pair> is outside the intersection table", citing the pair. A refusal must not promise a reorder that refuses one node later. The editor adds a one-action "move <op> after <op>" composite over `SetParam` (session-level, as cascade delete is; no new `DocEdit`, DM6 untouched), which the refusal can name; the API already has it as a rewrite.
