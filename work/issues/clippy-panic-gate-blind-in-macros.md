## From GitHub issue 454

opened 2026-08-13, 0 comments.

The workspace's panic-family lint gate — the enforcement mechanism for D9's "the kernel never panics on any input" — does not apply to code written inside a `macro_rules!` body. **clippy does not lint inside `macro_rules!` expansions.**

`[workspace.lints.clippy]` sets `unwrap_used`, `expect_used`, `panic`, `unreachable`, `todo`, `unimplemented` to `warn`, and CI runs `-D warnings`, so these are hard errors — everywhere except inside a macro body, where they are silently invisible.

## Repro

Verified independently on this toolchain (clippy 1.97.0):

```rust
// [lints.clippy] expect_used = "warn"
macro_rules! make { ($n:ident) => { pub fn $n(v: Option) -> u32 { v.expect("in macro") } }; }
make!(from_macro);
pub fn written_directly(v: Option) -> u32 { v.expect("direct") }
```

`cargo clippy` warns **once**, on `written_directly`. The macro-generated `expect` produces no diagnostic.

## How it surfaced

Found during review of #447. The curve API is generated by `nurbs_curve!`, and an intermediate revision of that branch carried three

```rust
.expect("locate_spans returns a nonempty first span")
```

calls inside the macro body. CI was fully green with them present. They have since been removed by that PR, so there is no known live instance today — but nothing caught them, and nothing would catch the next one.

## Scope

`crates/*/src/` currently contains 10 `macro_rules!` bodies across 9 files:

```
crates/editor-core/src/persist/strict.rs
crates/editor-core/src/program.rs
crates/geom-curves/src/nurbs.rs
crates/geom-curves/src/projection.rs
crates/geom-curves/src/fit.rs
crates/pncad-py/src/py/quantity.rs
crates/pncad-py/src/py/path.rs
crates/quantity/src/lib.rs
crates/topo/src/review_m1_pr5_internal.rs
```

Two of those files contain panic-family calls at all: `topo/src/review_m1_pr5_internal.rs` (16) and `geom-curves/src/fit.rs` (1). **These are file-level counts, not confirmed to be inside macro bodies** — #447's review reports the remaining in-macro instances are in `#[test]` functions, where the lints are sanctioned anyway. Separating the two requires a proper audit; that audit is part of this issue, not a premise of it.

## Why it matters

D9 makes "no panics on any input" a ratified property, and this lint is how it is enforced rather than asserted. A gate that is trusted and has a hole is worse than a gate known to be partial: every reviewer who sees green clippy on a macro-generated API reads it as "no panic constructs here," and that reading is currently unfounded.

The exposure is not hypothetical — the curve evaluation API, one of the kernel's hottest and most-used surfaces, is entirely macro-generated.

## Possible directions

Not a recommendation; this needs a decision.

1. **One-time audit.** Hand-check the 10 macro bodies, record the result. Fixes today, not tomorrow.
2. **Token-grep CI check.** Scan `macro_rules!` bodies in `crates/*/src/` for panic-family tokens. Crude, no type information, will need an allow mechanism for `#[test]` bodies — but it catches the whole class and is cheap.
3. **Lint the expansion.** Run the panic-family lints over `cargo expand` output in CI. Most faithful, heaviest, and the mapping from a diagnostic back to source is poor.
4. **Keep macro bodies thin.** Have each macro delegate to a normal generic `fn` that clippy *does* see, so the macro only forwards. Structural rather than checked — in keeping with how #447 resolved its own indexing question — but it is a convention, and conventions decay unless checked (cf. `check-test-aggregation.sh`'s own rationale).

(2) and (4) compose: the grep becomes cheap to keep green once bodies are thin.
