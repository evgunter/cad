## What

**`tools/tess-lint`'s `identity()` turns a MISSING sizing block into `Reading::Absent` — a lane fact — which is `D202`'s defect on the consumer side of the same CSV.** Target `identity`, `tools/tess-lint/src/lib.rs:958-961` at `e524b5671`:

```
let col = |f: fn(&Nurbs) -> f64| r.nurbs.map_or(Reading::Absent, |n| Reading::Number(f(&n)));
```

and the block-presence entry just below it, `Reading::Tag(if r.nurbs.is_some() { "present" } else { "absent" })`. `Reading::Absent` and `"absent"` are the lint's spelling of *"this face is not on the sized lane"*, and `map_or` cannot distinguish that from *"the row's sizing tail was empty for some other reason"* — which is precisely the reading `D202` refused on the producing side, one crate over.

`D202` closed (PR 1642) by refusing the state where it is derived (`tess_meter::sizing_of`) and again where it is written (`FaceRow::csv_row`). This site was identified as its consumer mirror in that lane and deliberately left alone. The disclosure is real; what it did not have was a schedule.

## Was

Filed by the style review of PR 1642 (Track K's tess-meter unit), which observed that this lane's two other disclosures got issue files and this one got only a sentence in a PR body. `D202`'s own residue.

## Finding

**This is weaker than `D202` was, and the row should say so before anyone spends a lane on it.** On the producing side the empty tail was a claim the crate could assert about its own lookup, so refusing it cost nothing. Here the lint's input is committed CSV text it did not produce:

- `parse` reads a row's sizing columns as a group and yields `Option<Nurbs>`. An EMPTY tail is what a legitimately off-lane row looks like, so `None` is the honest reading of the bytes. There is no third state in the file to distinguish.
- What `identity()` cannot see is a row whose chart says the face is on the sized lane and whose tail is empty anyway — the state `csv_row` now refuses to write, so no CSV this tree produces carries it. The lint parses `docs/tess-budget-data/`, a committed cut of an older tree, which is the one place such a row could still arrive.

So the fix is not `map_or` → a refusal at every column. It is a **parse-time** question: whether `parse` should refuse a row whose `chart` is a sized-lane tag and whose tail is empty, the way the producer now refuses to write one — and whether refusing it is right for a consumer whose stated design is to fail as a PARSER when the producer's schema moves (`tools/tess-lint`'s manifest). A refusal there also interacts with `D213`, which asks whether the block-presence entry in `IDENTITY_COLUMNS` still has a stated reason at all.

**Blind spot of this filing.** The sweep behind it was for `map_or(Reading::Absent, ..)` and the `is_some()` tag beside it, in one file. It did not walk the lint's other readers of an absent column, nor `scripts/` consumers of the same CSV.
