## Closed (2026-09-11) — both halves landed

**The `loop_area` half was exactly as cited.**
`crates/geom-brep/src/props/loop_area.rs:165-166` called
`span.eval_in_span(t)` and `span.deriv_in_span(t)` at one `(span, t)`
inside `nurbs_vector_area`'s Gauss loop; it is now one
`span.ders1_in_span(t)` destructured into the pair. The row's warning
about `ders_in_span` was right and was not taken: the order-2 door
would compute and discard `C″`.

**Bit-identity held, and nothing moved.** `ders1_in_span`'s own claim
is that its point is `eval_in_span`'s bit for bit and its derivative is
`deriv_in_span`'s bit for bit; the claim is pinned by
`ders1_in_span_is_eval_and_deriv_bit_for_bit`
(`crates/geom/src/curves.rs:1145`), which was EXECUTED rather than read
and passes. Nothing moved: no golden, no committed
render cell and no k-lint baseline changed on the branch, across the
twelve `test (…)` jobs, the five `k-lint (gate, …)` unifications and
the render lanes of the hosted run named in the PR. Locally the whole
of `geom-brep` is green (450 tests), including `r2_cert6_probes::r2_dome_gauge_silence_and_area_bit_invariance`,
which is an area-bit test on the path this site feeds. The door's
bit-identity claim is now exercised at a second, production site
rather than only in the test that asserts it.

**The `offset_fit.rs` half's citation had drifted, as the plan warned.**
The row cited `:432-437`; the note is at
`crates/geom-brep/src/offset_fit.rs:647`, on the `pub use
geom::OffsetCertificate;` re-export beside the fit door, and it has
been there unchanged since at least 2026-08-15 (`git show` at that
date puts the same text at the same line), so `:432-437` never named
it. `:432-437` today is inside `OffsetFitError::BoundNotFinite`'s
fields.

The note said the record type has to sit below the surface enum, that
its derivation is this module's, and that every limb writes into it —
true, and read together an implication that an `OffsetCertificate` only
ever exists at the derivation's scalar. It now states the split the row
asked for: the DERIVATION is `f64`-only (every door in the module takes
and returns `NurbsSurface<f64>`, checked across all eleven `pub fn`s),
while the RECORD carries no scalar parameter and travels verbatim onto
a lifted surface through `ApproxSurface::map_scalar`
(`crates/geom/src/surfaces/approx.rs:316-322`), so it DOES reach
consumers at scalars this module never runs at.

**One correction to the row's wording, made at the site.** The row
says the record travels "as provenance the validator never trusts",
which is right at `f64` and incomplete elsewhere. At `f64` the
validator re-derives against the description and never consults the
stored copy. At a scalar with no re-derivation lane
(`PropsQuadLane::recertify_approx` answering `None`,
`crates/topo/src/props.rs:925`) tier 3 does not merely distrust the
carried record — it REFUSES the face,
`ValidationError::ApproxLaneUnsupported`
(`crates/topo/src/validate.rs:3323`). The note says that, which is also
the row's own parenthetical ("the lane refuses because no re-derivation
exists at that scalar, never because no value can arrive") stated where
a reader of the record meets it.
