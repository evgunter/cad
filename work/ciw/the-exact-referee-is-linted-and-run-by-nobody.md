`crates/mesh/tests/nurbs_exact_referee.py` computes in exact rational
arithmetic the seven `truths` rows that
`crates/mesh/src/nurbs_cert.rs`'s
`the_described_bilinear_rationals_true_second_partials_are_under_the_certified_sups`
(`:3138`) asserts against, pasted at `:3206-3208` ("Generated by `python3
crates/mesh/tests/nurbs_exact_referee.py --rust`"). CI lints the script
(`scripts/check-python-lint.py`, `ci.yml:268`) and never runs it, so its own
`assert`s in `sqrt_rounded_down` never execute and nothing ties the Rust table
to what the script prints.

Neither side has changed since 2026-09-22, so no incident has followed, and a
per-PR test that shells out to Python is not worth its slot in the mesh shard.
A nightly step is free to PR latency and deterministic (exact arithmetic, no
seed), so it cannot add a flaky red.

The repair: one step in `nightly.yml`'s `python` job that runs
`python3 crates/mesh/tests/nurbs_exact_referee.py --rust` and compares its
literals with the `truths` block in `nurbs_cert.rs` (a short extraction by the
"Generated by" marker, or the script gaining a `--check FILE` mode that does
it), failing on any difference.

What would close it: the nightly python job runs the referee and fails when its output and the Rust table disagree.

- 2026-11-22 — **Reformulated by CIW triage** (the earlier body is in git history): Proposes a per-PR mesh test that shells out to Python. Neither the referee nor the table (`nurbs_cert.rs:3206`) has changed since 2026-09-22, so there are no incidents.
A nightly step costs PR latency nothing, and exact arithmetic cannot flake.
