## Closed (2026-09-04, CIW): neither failure is live, and the class half moved

Checked against main rather than inherited from the 2026-08-29 write-up.

**Failure 1 was already fixed** when this issue's own second comment
said so: `cert/main-pyo3-repair` (PR 1239, merged `5859c8c6`) repaired
the `create_exception!` invocation. `crates/pncad-py/src/py/mod.rs` now
carries ten of them and the wheel builds.

**Failure 2 is not a failure.** The `viewer` bin/lib doc filename
collision is real and still printed, but it is a **cargo** diagnostic,
not a rustdoc one, so `RUSTDOCFLAGS="-D warnings"` cannot reach it and
the pass does not fail. Measured on `1.97.0`, this tree:

```
$ RUSTDOCFLAGS="-D warnings -A rustdoc::private_intra_doc_links" \
  cargo doc --no-deps --document-private-items --bins --examples -p viewer --all-features
warning: output filename collision at target/doc/viewer/index.html
  = note: the bin target `viewer` ... has the same output filename as the lib target `viewer` ...
    Finished `dev` profile
EXIT=0

$ scripts/doc-gate.sh --pr --scope '--workspace'
doc-gate OK: the workspace pass renders under --pr, over --workspace —
library, binary and example targets alike.
EXIT=0
```

So the fix this issue asks for (rename the `[[bin]]` target, or
`doc = false`) has nothing to repair. Whatever reddened
`rustfmt + rustdoc (gate)` on run 33273557342, the collision line was
the visible diagnostic and not the cause; the run's logs are past their
14-day retention and the tree it ran on is 6 days of merges back, so
the cause is not now recoverable and is not worth recovering — the gate
is green on the tree we have.
