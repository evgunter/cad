## Finding

### S159. The compound-`Bounds` allowlist is file-granular, so ratifying one bound in a file ratifies every bound later added to it

**[verified]** Found by the F-e verification pass, alongside S158 (row `D102`) and **recorded separately because it is a different mechanism and will outlive whatever the matcher does.** Every entry in `bounds-allowlist.sh` is a path: `^crates/geom-brep/src/(pcurve_cache|ssi|ssi/certify|edge_nurbs)\.rs$` and so on. The ratification argument in the header is per-*seam* and often per-*function* — `probe_tube_chart` is justified by what that one body does — but the enforcement is per-*file*. A second, unrelated compound bound added to any allowlisted file inherits the first one's ratification silently.

This is the same shape as S63's `linalg/mat.rs` (allowlisted wholesale to resolve a false positive, now unguarded for the genuine case), except that here it is the *design* of every entry rather than one bad entry.

The cheap half is that the header already writes the per-seam argument, so the information exists; what does not exist is any check that a file's current bounds are the ones argued for. Options a taker should weigh rather than assume: line-scoped or symbol-scoped entries; a count pinned per file; or accepting file granularity and saying so at each entry.

## Landed

**Option taken: the pinned per-file count** — the third of the three the
finding offers (line- or symbol-scoped entries; a count pinned per file;
accepting file granularity and saying so). Symbol-scoped entries need
each hit's enclosing item, which is a parser and not a grep; accepting
the granularity changes nothing.

**Entry format.** `scripts/gates/bounds-allowlist.sh`'s file list is an
array of `PATH COUNT RULING` entries, one per ratified file, each under
the prose argument that earned it. The path feeds the scan's exclusion;
the count is the number of matcher OCCURRENCES the file carries,
re-derived on every run and compared with the pin; the ruling names the
argument the diagnosis sends a reader to. A malformed entry — no ruling,
a count that is not a positive decimal integer, a duplicate path — is
refused before any scan.

**Two disclosed costs**, both stated at `KNOWN GAP 6` and planted:

- **Substitution.** One ratified bound replaced by an unrelated one at
  the same count is invisible. Separating them is the per-symbol entry
  this option did not take.
- **Occurrences, not bounds.** The reading counts `+`-adjacent
  `…Bounds`/`…Enclosure` occurrences (or one, for a record caught only
  as a trait declaration), so `T: Decide + Bounds + CertifiedEnclosure`
  is one parameter's bound and two occurrences. It is stable and
  re-derived, which is what a pin needs; it is not a budget on bounds.
  Counting RECORDS instead was tried first and is blind to a second
  bound written on a line that already holds one.

**Not closed by this row**: `separation.rs`'s fourth compound bound
(`SolidSeparation::of`) rests on that struct's own doc rather than on the
M5 PR 8 ledger entry its allowlist entry cites, and owes a ledger row of
its own. The entry says so; the row is PROPS's.
