## What

**A per-column admissions table cannot state a cross-column invariant, and the class now has two instances filed nowhere together.** `tess-lint`'s `Admissible::Extent` documents that the trim box's own non-degeneracy (`u0 < u1`, `v0 < v1`) is beyond what its per-column table can say; `D200` was the same shape one crate over (`Band::new`'s `zero < escalate`, which `lint_csv` had to check in the harness voice because `Admissible::BandThreshold` is per column). Both instruments answer it the same way and neither says so at the other's site. The row is the **rule** — where a cross-column check belongs when the admission table is per column — not either instance.

(`D200` is a landed row and is not a tracker item; it is cited here as provenance only.)

## Closed

Landed as METER unit 3, branch `meter/d203-cross-column-rule`.

**The rule's home is `tools/README.md`, clauses `CC1`–`CC5`**, cited
by path and by id from every site in both instruments. The precedent
is `scripts/gates/README.md`: a design page beside the code it
governs, where the governed code is not one crate. It is a `tools/`
DIRECTORY page and not a page inside one lint, because the rule's
subject is two lints and a shared rule hosted inside one of its two
consumers is the shape that drifts. `k-lint` cites it by path, which
is what a citation across two separate cargo roots can be — there is
no shared rustdoc graph and no shared constant, by the same design
that makes `EXPECTED_HEADER` a restatement rather than an import.

**The row said two instances; there are nine.** The count is what
makes the rule owed rather than paraphrasable:

| Instance | Disposition |
| --- | --- |
| `k-lint` `band_zero < band_escalate` (`D200`) | `CC3`, at `lint_csv` |
| `k-lint` `Admissible::Margin` against `outcome` | `CC2`, folded into `admits`' signature |
| `tess-lint` `worst_dev`'s two `NaN`s against `dev_samples` | `CC3`, at `parse` |
| `tess-lint` the lane pairing, `chart` against the sizing tail | `CC3`, at `parse` |
| `tess-lint` the sizing tail's all-or-none presence | `CC3`, at `parse`, over a block |
| `tess-lint` `Admissible::Extent`, the trim box's `u0 < u1` | `CC3`, at `parse` — **written by the fix pass, having been wrongly dispositioned as entailed** |
| **`tess-lint` `cap_bands` / `snap_bands` against `bands`** | **`CC3`, at `parse`, written by this unit** |
| **`tess-lint` `patch_cells` against `nu · nv`** | **`CC3`, at `parse`, written by the fix pass** |
| **`tess-lint` `opt_cells` against `patch_cells`** | **`CC3`, at `parse`, written by the fix pass** |

The lane pairing IS an instance of the class and was checked as one
rather than assumed: it refuses at `parse`, in the harness voice, over
two columns that `Admissible` polices singly, and its own comment
already called itself *"the second cross-column rule"* four commits
after `D203` was filed. That is the evidence the rule needed a home.

**Where a check goes, and in which voice, is now decidable from the
text.** `CC1`: at the crate's reading boundary — `tess_lint::parse`,
`k_lint::lint_csv` — which are the same place and not two answers,
since `lint_csv` parses and scans in one pass because k-lint keeps no
row type. `CC2` when one column is PRIOR (the discriminant becomes an
argument to `admits`); `CC3` when neither is (checked beside the
table, once, where both readings are in hand). `CC4` says there is no
third answer: a property the producer's code makes unreachable is
checked anyway, because the boundary cannot see the producer's code.
`CC5` is the voice — harness, always — and the test is not "does it
span columns" but `Report`'s own, which the page cites rather than
restating a third time.

**`CC4` was written the other way round and was false.** It said the
trim box's non-degeneracy is a property no row surviving the
per-column table can violate, and stated the entailment
(`span_opt_cells`' floor) in place of a check. A row carrying
`u0 = u1 = 0e0` beside `span_opt_cells = 2.5e1` satisfies every
per-column entry and reaches rule 4's `identity` as a face-identity
reading. The true criterion was "no row THIS PRODUCER writes", which
is producer-correctness — the assumption `tools/tess-meter`'s own
header refuses on the way in: *"A parse guard bounds what a column may
SAY; it cannot know whether the producer measured it."* Inverting the
clause rather than conditioning it is what removes the exemption; the
entailment also lived in a second crate and a second cargo root, where
nothing could tell whoever edited it what depended on it.

`CC5` is what keeps the rule from over-firing, and the sweep needed
it: an admission refuses what the producer could not have written,
never what the instrument exists to measure. `cap_bands` counts a
subset of `bands`, so a larger one is arithmetic that did not happen.
`grid_cells` against `span_opt_cells` looks identical and is the
`split` ratio the report is FOR — the committed baseline carries rows
on both sides of it, so it is not an invariant at all, and refusing it
would be the instrument refusing its own subject. **That reasoning is
about that one pair and does not generalise to "optimality
relations":** `opt_cells ≤ patch_cells` has the same surface shape and
is a minimum against the value its own seed produced, which is why the
fix pass checks it.

**Every guard reds under its own negation, and each was run.** The
three `parse` checks red with the guard removed and red again with the
comparison widened or narrowed by one step; the citation guards red
when a clause heading is renamed, when a clause is added, and (as a
compile error, in both crates) when the page moves. Nothing committed
is rejected: all 64 sized rows of
`docs/tess-budget-data/tess-budget-baseline.csv` pass every one of
them, with `cap_bands == bands` on 64 of 64 and
`opt_cells == patch_cells` on 6 of 64 — the equality cases are the
dataset, not a corner of it.

**Filed, not fixed:** `tess-lint-zero-certificate-two-meanings`.
`Admissible::Certificate` admits `worst_cert = 0` as *"a face whose
triangles are exact"*; `mesh::budget` says it also spells a face that
refused before the emit pass and certified nothing. Same shape as
`worst_dev`'s two `NaN`s. The discriminant the kernel names
(`dev_samples`) is dead on the fresh `--sizing-only` sweep and LIVE on
the committed baseline the same gate reads through the same `parse`;
what the row still lacks is a per-row separation of the two states,
which starts in `crates/mesh`.
