## What

**A per-column admissions table cannot state a cross-column invariant, and the class now has two instances filed nowhere together.** `tess-lint`'s `Admissible::Extent` documents that the trim box's own non-degeneracy (`u0 < u1`, `v0 < v1`) is beyond what its per-column table can say; `D200` was the same shape one crate over (`Band::new`'s `zero < escalate`, which `lint_csv` had to check in the harness voice because `Admissible::BandThreshold` is per column). Both instruments answer it the same way and neither says so at the other's site. The row is the **rule** — where a cross-column check belongs when the admission table is per column — not either instance.

## Closed

Landed as METER unit 3, branch `meter/d203-cross-column-rule`.

**The rule's home is `tools/tess-lint/README.md`, clauses
`CC1`–`CC5`**, cited from every site in both instruments. It is the
repo's first `tools/*/README.md`, and it follows
`scripts/gates/README.md`'s precedent — a design page beside the code
it governs, where the code is not one crate. `tools/tess-lint` is that
place because it carries five of the seven live instances, four
checked and the one that is checked nowhere; `k-lint` cites it by path, which is
what a citation across two separate cargo roots can be (there is no
shared rustdoc graph and no shared constant, by the same design that
makes `EXPECTED_HEADER` a restatement rather than an import).

**The row said two instances; there were six, and the sweep added a
seventh.** The count is what makes the rule owed rather than
paraphrasable:

| Instance | Disposition |
| --- | --- |
| `k-lint` `band_zero < band_escalate` (`D200`) | `CC3`, at `lint_csv` |
| `k-lint` `Admissible::Margin` against `outcome` | `CC2`, folded into `admits`' signature |
| `tess-lint` `worst_dev`'s two `NaN`s against `dev_samples` | `CC3`, at `parse` |
| `tess-lint` the lane pairing, `chart` against the sizing tail | `CC3`, at `parse` |
| `tess-lint` the sizing tail's all-or-none presence | `CC3`, at `parse`, over a block |
| `tess-lint` `Admissible::Extent`, the trim box's `u0 < u1` | `CC4`, entailed by `span_opt_cells`' floor; checked nowhere |
| **`tess-lint` `cap_bands` / `snap_bands` against `bands`** | **`CC3`, written by this unit** |

The lane pairing IS a third instance of the class and was checked as
one rather than assumed: it refuses at `parse`, in the harness voice,
over two columns that `Admissible` polices singly, and its own comment
already called itself *"the second cross-column rule"* four commits
after `D203` was filed. That is the evidence the rule needed a home.

**Where a check goes, and in which voice, is now decidable from the
text.** `CC1`: at the crate's reading boundary — `tess_lint::parse`,
`k_lint::lint_csv` — which are the same place and not two answers,
since `lint_csv` parses and scans in one pass because k-lint keeps no
row type. `CC2` when one column is PRIOR (the discriminant becomes an
argument to `admits`); `CC3` when neither is (checked beside the table,
once, where both readings are in hand); `CC4` when a per-column policy
already refuses every violating row (state the entailment, check
nothing). `CC5` is the voice: harness, always, and the test is not
"does it span columns" but `Report`'s own — *would the gate otherwise
assert something false about a MEASUREMENT*.

`CC5` is also what keeps the rule from over-firing, and the sweep
needed it: an admission refuses what the producer could not have
written, never what the instrument exists to measure. `cap_bands`
counts a subset of `bands`, so a larger one is arithmetic that did not
happen. `grid_cells` against `span_opt_cells` looks identical and is
the `split` ratio the report is FOR — the committed baseline carries
rows on both sides of it, so it is not an invariant at all, and
refusing it would be the instrument refusing its own subject.

**The one instance this unit wrote reds under its own negation.**
`an_indicator_count_above_bands_is_harness_breakage` fails with the
guard removed, and fails again with `>` widened to `>=` — equality is
a reading (every emitted band bound by the same constraint) and the
test pins that direction too. It rejects nothing committed: no sized
row of `docs/tess-budget-data/tess-budget-baseline.csv` violates the
containment.

**Filed, not fixed:** `tess-lint-zero-certificate-two-meanings`.
`Admissible::Certificate` admits `worst_cert = 0` as *"a face whose
triangles are exact"*; `mesh::budget` says it also spells a face that
refused before the emit pass and certified nothing. Same shape as
`worst_dev`'s two `NaN`s, but the discriminant the kernel names
(`dev_samples == 0`) is `0` on every row of the `--sizing-only` sweep
CI gates on, so there is nothing in the row to refuse it with. Closing
it starts at the producer, outside this fence.
