## What

**`tools/tess-lint`'s `identity()` turns a MISSING sizing block into `Reading::Absent` — a lane fact — which is `D202`'s defect on the consumer side of the same CSV.** Target `identity`, `tools/tess-lint/src/lib.rs:958-961` at `e524b5671`:

```
let col = |f: fn(&Nurbs) -> f64| r.nurbs.map_or(Reading::Absent, |n| Reading::Number(f(&n)));
```

and the block-presence entry just below it, `Reading::Tag(if r.nurbs.is_some() { "present" } else { "absent" })`. `Reading::Absent` and `"absent"` are the lint's spelling of *"this face is not on the sized lane"*, and `map_or` cannot distinguish that from *"the row's sizing tail was empty for some other reason"* — which is precisely the reading `D202` refused on the producing side, one crate over.

`D202` closed (PR 1642) by refusing the state where it is derived (`tess_meter::sizing_of`) and again where it is written (`FaceRow::csv_row`). This site was identified as its consumer mirror in that lane and deliberately left alone. The disclosure is real; what it did not have was a schedule.

## Was

Filed by the style review of PR 1642 (Track K's tess-meter unit), which observed that this lane's two other disclosures got issue files and this one got only a sentence in a PR body. `D202`'s own residue.

## Finding

**This is weaker than `D202` was, and the row should say so before anyone spends a lane on it.** On the producing side the empty tail was a claim the crate could assert about its own lookup, so refusing it cost nothing. Here the lint's input is committed CSV text it did not produce:

- `parse` reads a row's sizing columns as a group and yields `Option<Nurbs>`. An EMPTY tail is what a legitimately off-lane row looks like, so `None` is the honest reading of the bytes. There is no third state in the file to distinguish.
- What `identity()` cannot see is a row whose chart says the face is on the sized lane and whose tail is empty anyway — the state `csv_row` now refuses to write, so no CSV this tree produces carries it. The lint parses `docs/tess-budget-data/`, a committed cut of an older tree, which is the one place such a row could still arrive.

So the fix is not `map_or` → a refusal at every column. It is a **parse-time** question: whether `parse` should refuse a row whose `chart` is a sized-lane tag and whose tail is empty, the way the producer now refuses to write one — and whether refusing it is right for a consumer whose stated design is to fail as a PARSER when the producer's schema moves (`tools/tess-lint`'s manifest). A refusal there also interacts with `D213`, which asks whether the block-presence entry in `IDENTITY_COLUMNS` still has a stated reason at all.

**Blind spot of this filing.** The sweep behind it was for `map_or(Reading::Absent, ..)` and the `is_some()` tag beside it, in one file. It did not walk the lint's other readers of an absent column, nor `scripts/` consumers of the same CSV.

## Closed

Landed with `D213` as METER unit 1, branch
`meter/d213-d214-sizing-block`. The `:958-961` citation is at
`e524b5671` and no longer resolves — unit 0 reworked the same file
first, and the `is_some()` tag beside the `map_or` is now spelled
`Row::is_sized()`.

**The filing's own analysis stands and is not undone.** `map_or` is
untouched. `parse` still reads the sizing columns as a group and still
yields `Option<Nurbs>`; an empty tail is what a legitimately off-lane
row looks like and `None` is the honest reading of those bytes. What
changed is upstream of it.

**The refusal is taken, at parse, in BOTH directions.** `parse` now
refuses a row whose `chart` is one of `SIZED_CHART_TAGS` over an empty
sizing tail — the state `tess_meter::FaceRow::csv_row` refuses to
WRITE — and, with it, the other cell of that same 2x2: an unsized
chart carrying the sizing columns anyway. Refusing only the first would
have left `is_sized()` a function of `chart` in one direction only,
which is not enough to retire `D213`'s entry. It is the right shape for
this consumer because both cells are the producer's schema having moved
under the crate, and this crate's stated design is to fail as a PARSER
when that happens — the treatment `EXPECTED_HEADER` and `CHART_TAGS`
already get, and the reason the module header now names TWO
cross-column refusals rather than one.

`CHART_TAGS` is not narrowed. `SIZED_CHART_TAGS` is a new, separate
roster — a proper subset of it, restating `tess_meter::Chart::sized_lane`
— and the doc says why the two cannot be widened alike: `CHART_TAGS` is
deliberately broad because an unwritten tag simply never arrives, while
every extra member of the sized roster weakens the pairing on rows that
do arrive.

**It rejects nothing committed.** Over
`docs/tess-budget-data/tess-budget-baseline.csv` at the merge base:
1353 rows, 64 `nurbs` rows all with a full tail, 1289 rows on the five
unsized charts all with an empty tail, no partial tail, no row in
either refused cell. Re-taken over every committed BLOB of that path in
the history. What was enumerated: the distinct blob ids at that path
over every ref (`git log --all --full-history --format=%H -- <path>`,
then `git rev-parse <commit>:<path>`, de-duplicated) — **20 blobs**,
reached by 108 commits under default history simplification and 305
with `--full-history`. Those 20 carry **12 distinct row counts, 1025 to
1353, 24763 rows in all**, and **4 distinct header shapes, all of them
carrying `triangles`**; 16 of the 20 blobs are `EXPECTED_HEADER` byte
for byte and the other 4 are earlier column sets `parse` refuses at the
header before reading a row. The pairing was counted over all 20
regardless, by column position rather than through `parse`, since every
one of the four shapes has the sizing tail starting at `u0`:
**zero rows in either refused cell and zero partial tails**. The chart
column over those 24763 rows is `plane` 17741, `sphere` 2804,
`cylinder` 1581, `nurbs` 1280, `torus` 1077, `cone` 280 — and `approx`
zero, which is why `SIZED_CHART_TAGS`' second member is exercised only
by this crate's fixtures and the constant's doc now says so. The
suite's own standing evidence is that `tests/baseline_census.rs` parses
the committed file on every run.

**An earlier draft of this paragraph said 127 blobs and 27 excluded
pre-`triangles` header shapes.** Neither reproduces: the 127 was a
commit-touch count read as a blob count, and no committed blob at this
path predates the `triangles` column. The row-count figures and the
conclusion are unchanged.

**The sized roster's membership is pinned across the cargo-root
boundary**, and the pin is written rather than deferred:
`tools/tess-meter/tests/derivations.rs`'s
`the_lints_sized_roster_answers_sized_lane_for_every_tag_this_crate_emits`
reads `SIZED_CHART_TAGS` out of `tess-lint`'s source (the locator
`CHART_TAGS`' pin already uses) and asserts membership equals
`Chart::sized_lane` on every tag `EVERY_CHART` names.
Per-tag biconditional rather than equality, for the reason the
`CHART_TAGS` pin is containment: the lint parses baselines cut from
older trees, so a chart the meter retires has to stay in both rosters
while a committed row carries it. Its own falsification guard
constructs both failures — a roster short a sized tag, and a roster
carrying an unsized one — and separates each from the real thing.
Without it, the only guard on the split was a written-out literal
inside the test that reads the constant.

**The refusal ORDER is pinned.** `parse` now has three refusals over
the same token, and nothing held their sequence:
`an_unknown_tag_is_refused_for_being_unknown_before_the_pairing`
asserts the roster speaks before the pairing (a tag the crate does not
know cannot be judged against `SIZED_CHART_TAGS` at all) and that the
pairing speaks before `face` (the schema move is the fault that
explains the unreadable count). Both halves were proved red — the first
by swapping the two blocks, the second by removing the pairing arm.
