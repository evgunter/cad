## What

**`mesh::sizing::ceil_count` answers `1` for a NEGATIVE step**, in the function about to allocate that many grid points: `raw` is negative, finite, and floors to one, so it refuses only what makes `raw` non-finite (a NaN, a zero step, a count ≥ 2^24). `tess_meter::divisions`, the consumer-side second spelling, now refuses a negative step under `D105`, so **the kernel is the laxer of the pair** — and a negative step is not a smaller grid, it is a reading that did not happen. The fail-loud side of a two-spelling pair should be the one holding the allocation. Unreachable today only because every step reaching it is `sqrt`- or `cap_angular`-derived.

## Closed (2026-10-20, `tess/ceil-count-refuses-a-non-positive-step`)

`ceil_count` reads four non-ordinary steps, each stated in its doc:
- **sign bit set or NaN:** refuses as the new
  `TessellateError::StepNotPositive { span, step }`, worded as a kernel
  defect;
- **`+0.0`:** stays `ResolutionOverflow` (the underflow end of a positive
  step, from a δ so fine its step rounds to zero);
- **`+∞`:** stays one cell. It is the "nothing constrains this
  direction" reading, which 9 mesh rows reach on straight NURBS
  directions through `nurbs_cert`'s `split_steps`/`grid_steps`, whose
  doc already states the contract ("`f64::INFINITY` for a direction
  nothing constrains; `ceil_count` turns that into one cell"). With
  both ends stating it, and the count its only reader, no item is
  filed for typing it: an `Option` would ripple through `SplitSteps`
  and the aspect solve without changing any decision.

Row `sizing::tests::a_step_that_is_not_a_length_refuses_before_any_count`:
−1, −0.0, −1e-300, −∞ and NaN refuse; +0.0 overflows; +∞ answers 1. It
goes red on the old floor-to-1 (`step -1: Ok(1)`). The existing unit
row's NaN expectation moved from `ResolutionOverflow` to the new
variant. Probed before the change: no caller hands the count a
negative step.
