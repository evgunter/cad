## Finding

The two scaffold-strut mint sites in `step-import`'s `assemble.rs` hold
the zero-length hazard to different standards (`plant` guards bitwise
coincidence; `insert_selfloop_tied` mints at `p.x + 1.0` with no
argument — at |p.x| ≳ 2⁵³ that IS `p.x`; **unsure** on reachability,
sure on the asymmetry). The printable-ASCII band `0x20..=0x7E` is
spelled independently three times across the three boundary crates —
three formats' genuinely separate rules sharing a constant. And
`pncad-py` mints two literal tags (`"no_minted_id"`, `"name_serialize"`)
against `Doc.new`'s stated through-`crate::tags` rule — no kernel enum
exists behind either, so the question is whether the rule's statement
should carry the exception (**unsure**).

## Four of the finding's premises are wrong, corrected here

Read against the tree on 2026-09-15 by the lane that took the row, and
extended by its style review. The finding above is left as written;
these are the corrections, each with what was checked. Two of them
(1 and 2) the dispatching spec had already caught; two (3 and 4) are
errors the spec itself carried.

1. **"three formats' genuinely separate rules" — it is two formats,
   three sites.** `crates/step-import/src/parse.rs`'s `string_body`
   and `crates/step-export/src/lib.rs`'s `quoted` are both **Part
   21's basic alphabet**, read and written: one rule, two crates, and
   each doc comment says Part 21 by name. Only
   `crates/stl/src/options.rs`'s `SolidName::new` is independent — it
   is what an ASCII-STL `solid` line can carry. The row counted
   crates; the question is about formats, and the answer turns on it:
   the two STEP sites owe each other a disclosure, the STL site owes
   the opposite one.

2. **"no kernel enum exists behind either" — false for
   `no_minted_id`.** `crates/pncad-py/src/tags.rs`'s
   `declare_error_tag` maps `DeclareError::NoMintedId` to exactly
   `"no_minted_id"`, and `src/tests.rs`'s
   `declare_error_tags_are_stable` pins it. So that literal was not a
   rule-exception at all but a **collision**: two doors (`Doc.insert`
   and `Doc.declare`) publishing one word for one state, neither
   knowing the other existed. It is true for `name_serialize`, which
   is a `serde_json` failure with no arm anywhere.

3. **The two `no_minted_id` paths were already identical on the
   wire**, which the row and the spec both supposed otherwise. Both
   reach Python as `ErrorClass::Edit`; `boundary_edit_err` passes
   `EditPayload::NONE` and no inner variant, and `declare_err`'s
   `NoFindings | NoMintedId` arm passes `(None, EditPayload::NONE)`
   too — the same `edit_fields` call with the same three arguments.
   Only the human message differed. So the collision cost a caller
   nothing it could observe, which is why it survived; what it cost
   was that a rename in one place would have moved one of the two.

4. **`|p.x| ≳ 2⁵³` is wrong, and it is wrong on both sides.** The row
   says the offset vanishes above that magnitude; the spec repeated
   it. Checked against the tree: it is not a threshold at all. In
   `[2^53, 2^54)` the offset is exactly half a step, so
   round-half-to-even decides on the value's own mantissa parity
   (`2^53` loses it, `2^53 + 2` keeps it); from `2^54` out it is
   always lost; and the negative side is the same picture shifted one
   binade, because a positive offset moves a negative coordinate
   toward zero into the finer binade — `-2^53 + 1.0` is exactly
   `-(2^53 - 1)`. `strut_endpoint`'s doc carries the checked
   statement and the test pins every boundary it turns on.

`plant`'s guard was also **bitwise**, as the row says, and that is
narrower than the question: the predicate should ask whether the
chord is zero-length, and value equality is that question. The `±0`
pair it newly catches is not reachable from a parsed file
(`crate::signed_zero` owns that argument, and `entities::as_real`
flushes every literal at the read) — the change is right because the
predicate now states what it asks, not because the case is live.

## Closed 2026-09-15

All three residues, on `port/s415-boundary-residues`.

1. `assemble.rs`'s two scaffold mints now hold one rule: `coincide`
   (value equality on all three components, so the two zeroes are one
   point) and `strut_endpoint`, which withholds the self-loop strut's
   far endpoint where the absolute offset vanishes into `p.x`'s own
   `f64` spacing. The site refuses `StepImportError::Topology`, the
   standing `plant` already gave the same state, instead of walking
   into the certification gate's own refusal — probed, and it reads
   *"the stored parameter interval is not forward ... a degenerate
   zero-span interval is refused by the same gate"*: loud, but about
   parameter intervals rather than about the file. Three rows in
   `assemble.rs`'s own test module pin it — the two tie bands on both
   parities and both edges, and the DOOR itself, driven with a start
   vertex whose coordinate swallows the offset. That branch is dead on
   the corpus (instrumented: zero hits across the whole `step-import`
   suite), so the door row sets the rotation system up directly and
   carries an ordinary-coordinate control. The offset's MAGNITUDE — `1.0`,
   absolute, in a format whose coordinates carry no unit contract —
   was deliberately not chosen here and is EXCH's
   `step-scaffold-strut-offset-is-absolute-in-a-unit-free-format`.

2. The duplication stays and stops being silent. Each Part 21 site
   names the other as a disclosed copy and says why the two are
   stated separately: the two crates share no dependency but the
   kernel, which is no home for a text-format constant
   (`docs/DESIGN.md`'s `## Layering` section, which carries no
   D-number); the edge that does exist is `step-import`'s
   DEV-dependency on `step-export` for the round-trip oracle, which
   cannot carry a shipped constant; and a leaf crate below both, the
   workspace's own precedent in `test-utils`, is a heavy answer for
   one range. The STL site says its equal band is a coincidence of
   two independent rules and is deliberately not shared. Both bounds
   and the two characters just outside them are now pinned at each
   STEP site, on the model of `crates/stl/tests/export.rs`'s existing
   row.

   The band was also stated **eleven** times across the three crates,
   of which the first pass disclosed three. Swept: the restatements
   with no reason to spell the numbers now point at the site that
   decides, leaving nine — three deciding matches, two user-facing
   refusal texts, three public docs and one bounds argument — each
   with a reason. The hit list is in the PR.

3. `Doc::insert` takes its word from `declare_error_tag` rather than
   restating it, so the synonym is one word by construction — ruled
   an intended synonym, since the two refusals are the same contract
   violation and were already indistinguishable on the wire.
   `name_serialize` stays minted at its site, and the rule's
   statement carries the exception: `boundary_edit_err`'s doc says
   the test is whether a kernel enum arm stands behind the refusal,
   not "always through `crate::tags`". The absence the row's question
   pointed at — nothing pins a boundary-minted tag's value, and
   nothing would have reported the collision — is LIB's
   `boundary-minted-refusal-tags-are-pinned-nowhere-and-share-the-kernel-namespace`.

The **M** class estimate held.
