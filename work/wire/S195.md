## Finding

**Raised by #836 (G7/S106) out of its own claim site.** The verb
vocabulary now has a table, a `Verb::ALL` and a cross-crate census. The
**arc-mode** vocabulary — which travels inside the verbs — had none of
the three when this was filed, and is spelled four times:

- six standalone spec structs in `profile/src/path/verbs.rs`
  (`Radius`, `Bulge`, `Via`, `Center`, `Sweep`, `ArcLen`), consumed by
  the state-keyed trait matrix;
- restated field-for-field as the six variants of `pub enum ArcData` in
  `profile/src/path/program.rs`;
- restated as `pub enum ProgramArcData` in `editor-core/src/program.rs`
  (the `Expr`-valued document form);
- restated as `enum WireArcData` in
  `editor-core/src/persist/wire.rs` (the persisted form).

The four spellings are still four. **Everything this row said about
their census has been overtaken**, and the corrected reading is below —
the four spellings are a layering consequence (`profile` has neither
`Expr` nor serde and by G1 must not gain them), not the finding.

### What the tree does today (2026-09-12, measured)

The row's four claims, each against the tree rather than against the
diff that moved it:

1. **"There is no `ArcData::ALL`" — STALE.** `arc_modes!`
   (`profile/src/path/program.rs`) declares each mode once and projects
   three artifacts from that declaration: `ArcData`'s variant, the
   `ArcMode` tag, and that tag's membership in `ArcMode::ALL`.
   `ArcData::mode()` is the read-back door. This is `transition_table!`'s
   construction one level down.
2. **"no census at all" — STALE, and by a factor of four.** `ArcMode::ALL`
   anchors four checks today: `every_arc_mode_is_a_document_program`
   (`editor-core/tests/switch_program_vocabulary.rs`), whose witness
   `mode_witness` is a MATCH on the tag rather than a list, so a mode
   with no document spelling is a compile error, not a failed assertion
   — but that is only the census's EXISTENCE limb, and the census has a
   second one that is a live assertion: it resolves each witness and
   compares `spec.mode()` against the mode asked for, which is the only
   check in the tree that catches the `res_spec` hop. That hop —
   matching the document vocabulary and CONSTRUCTING the kernel one — is
   what #836 and this row were both filed about, so the runtime clause
   is not a lesser half. Measured (WIRE's review of PR 2447): a
   `res_spec` arm changed to construct a neighbouring mode reddens
   `every_arc_mode_is_a_document_program` alone, with the bijection, the
   wire, the verb and the target clauses all green;
   `arc_mode_tags_are_injective` (`editor-core/src/eval/mod.rs`), which
   refuses two modes sharing a content-key word; `mode_class`
   (`pncad-py/src/surface_census.rs`), the Python roster; and the
   corpus generation in (3).
3. **"nothing forces the corpus to grow when a mode is added" — STALE,
   and it is the sharpest correction.** `chain_steps()` generates the
   `ArcTo` block and all three fused blocks (`FilletArc`, `ArcFillet`,
   `ArcFilletArc`) from `ArcMode::ALL` through `mode_witness`, so every
   mode rides the wire round-trip and the slot bijection in both spec
   positions without anyone remembering to add it. The VERB side of the
   same corpus is still a hand-written `Vec`, forced instead by
   `Verb::ALL` in the census below it.
4. **"a seventh mode's slot role would address nothing, SILENTLY" —
   WRONG, measured.** See the mutant below. The role is caught, at the
   first Height slot, by name.

`ProgramTarget`/`WireTarget` — the first of the three smaller pairs this
row lists — was closed by D364 / PR 2445 the same way: `TargetKind`,
`TargetKind::ALL`, `Target::kind()`, a target census, and
`target_witness` generating the corpus's form side.

### The mutant, and which guard fires

A seventh arc mode (`Height { h: T, target: Target<T> }`) was added to
`arc_modes!` and discharged the way a real implementer would. Twenty-one
sites are compiler-forced and one is not:

- **`profile` lib, 8**: `ArcData::target()`, and the seven replay
  dispatchers `do_arc_to_point`, `do_arc_to_directed`, `do_arrival`,
  `do_fused_point`, `do_fused_leg_end`, `do_fused_directed`,
  `do_fused_entry`.
- **`profile` tests, 2**: `cert4r1_e2e.rs`, `generic_replay.rs`.
- **`editor-core` lib, round 1, 4**: `arc_mode_tag` and both content-key
  `spec` hashers in `eval/mod.rs`, `spec_lit` in `program.rs`.
- **`pncad-py`, 1**: `mode_class`.
- **`editor-core` test, 1**: `mode_witness` — **the mode census, firing
  as a compile error**, which is the round-1 site that cannot be
  discharged in place. `spec_lit` can take a refusal arm and ship; this
  one cannot be satisfied without `ProgramArcData` learning the mode.
- **`editor-core` lib, round 2 (once `ProgramArcData` grows), 5**:
  `WireArcData::from_spec` and `into_spec`, `spec_slots`, `res_spec`,
  `spec_bit_eq` (whose mismatch arm names every variant rather than
  using `_`, so it is forced twice over).
- **NOT forced, 1**: `spec_arg_access!`, which still ends `_ => None`.

With every forced site discharged and `spec_arg_access!` left alone —
the row's exact scenario — **the bijection guard fires, by name**, and
it is the only red in `editor-core`'s 1224-test binary:

```
Profile { loop_: 0, step: 17, arg: HeightVal } is enumerated but addresses nothing
```

That names the role and the step. Discharged one notch lazier still —
`spec_slots`'s arm enumerating nothing at all — the count clause fires
instead, and that message named neither the mode nor the step: *"the
program has 133 expressions and enumerates 118 slots"*. That is the one
thing this row found still wrong, and PR 2447 fixes it: the clause now
re-runs its own comparison one chain step at a time on the failure path
and names them.

A third mutant, a mode LAUNDERED on the wire (`from_spec` mapping it onto
a neighbouring `WireArcData` variant — the one round-2 site whose
discharge can be lossy and still compile), is caught by
`every_document_verb_survives_the_wire`, because the corpus that clause
walks is generated from `ArcMode::ALL`. Its message localizes nothing;
that is filed as `wire-roundtrip-census-localises-nothing`.

### The two remaining pairs: risk is nil

`ArcSide`/`WireSide` and `ArcSweep`/`WireWinding` need no anchor.
`WireSide::from_side` matches `profile::ArcSide` and `into_side` matches
`WireSide`; `WireWinding::from_sweep`/`into_sweep` likewise. Both
directions are compiler-forced, so neither mirror can gain or lose a
variant the other lacks. The only residual hazard is a deliberately
lossy `from_*` arm, and it is not one worth an anchor: both enums are
binary by GEOMETRY rather than by convention — a half-plane bit and a
travel sense — so there is no third variant to add. Giving them an `ALL`
for symmetry with the three vocabularies that earned one would be
ceremony.

### One-census-or-four

Untouched here. PR 2445 answered the adjacent question by precedent (a
separate `target_forms!` rather than generalising `arc_modes!`), and the
prior question — what counts as the third instance that triggers
unification — is already
`work/wire/the-third-tag-vocabulary-macro-owes-a-unification-trigger.md`.
This row's measurement bears on it only by adding a data point: the
`ArcMode` and `TargetKind` macros now expand to the same three artifacts
plus a read-back door, and the two invocations differ only in whether a
variant carries fields.
