**Premise correction 2 — a file entity id is weaker than what the importer already uses, and is not sound** (sure). The parsed face spec does not keep its surface entity id; `adopt::attach_surfaces` instead puts every bit-identical surface in a solid on one kernel surface key. That is strictly stronger: one entity always gives one set of bits, so every entity-shared case is already shared, and it also catches identical surfaces a writer emitted as separate entities — our own `step-export` writes one surface entity per face (`writer.rs`, `advanced_face`), so on our own corpus entity ids show no sharing at all and bits do. And "same entity ⇒ same bits" fails after normalization: `knot_split` cuts one B-spline face into sub-patches with different nets, and the faces it mints keep the replaced face's id — an identity keyed on entity ids would call two different descriptions one source, the silent gluing the row feared. The knot split and the seamless-band re-mint also mint new ids through `mint()`, so the maps' keys are partly the reader's own invention, not the file's.

**What file identity would add under the current design: nothing a check can use.** The second structural rung (the coincidence door, evaluating each carrier with every variable symbolic) reads an imported carrier as a constant — import has no parameters (`[import]`, non-goal). Two cells reached through one read with bit-equal carriers differ by exactly zero, so the door proves them structural; two parts that touch only within ε have a nonzero exact difference and their contact is an `unproven-coincidence` finding, quieted by an assertion — exactly what `[import]` ratifies. Entity ids prove nothing the bits do not. Worked example: two placed copies of one bracket on a plate, all from one file. The copies' faces come from one entity, but they are different carriers (different maps, different bits); each meets the plate by value, so each contact is a finding — the right answer, and an entity id could not change it.

**Where file identity does belong: in names, when an import is a document node.** N6 names a recorded cell by the read it entered through and its name there. An imported body has no names today (`import_step` is a free function, `editor-core` never calls it; ASSEMBLY.md A8: "import-as-assembly-document is not implemented"). When that node is built, its name table is the one place file identity should live, under three constraints checked in the tree: a face's file id is not injective (after normalization a name needs the face id plus a piece index); copies are told apart by the occurrence, which the A7 record (`PlacedInstance`: occurrence, relationship, transform, applied map) already carries beside the body; and ids mean something only for one pinned file content (`[assemblies.pins]`), since other writers renumber on export.

**The answers as final states.**
- **A (recommended): close as superseded.** The import's provenance is what already travels beside the body — the A7 instance record and the reported normalizations; nothing is stamped on descriptions. Native and imported bodies are one kind of thing, as `[import]` says. Fully reversible: building the import node later loses nothing.
- **B: stamp a file-derived identity on descriptions** (the row's proposal). It brings back a kernel provenance channel that N6 just retired, states the same fact twice (bits/keys and stamps) to be kept in step by hand, has no reader, and is wrong after a knot split. Reject (sure).
- **C: build the import node now, with entity-id names.** The right home, but it is a feature (import-as-document) with no consumer asking for it, not a fix for this defect. Lean no, unless the feature is wanted for its own sake.
